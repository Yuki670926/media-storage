# 要件定義書(非機能要件中心)

本書は [DESIGN.md](DESIGN.md) に**先立つ**文書。設計判断はすべて本書の優先順位から導出する。両者が矛盾した場合は本書が勝ち、設計を直す。

本プロジェクトは、このリポジトリをクローンした**運用者(あなた)が Claude Code を使って実装・運用する**前提で文書化されている。発案者による決定済み事項と、運用者が最終決定する項目は末尾 §5 にまとめてある。✏️ マークは残っている仮置き値。

## 1. 機能要件(サマリ)

非機能要件が主題のため概要のみ。詳細は DESIGN.md。

| 優先度 | 要件 |
|---|---|
| 必須 | iPhone の写真・動画をオリジナル無劣化で自分のストレージへ保存できる |
| 必須 | 差分のみを自動でバックアップできる(手動操作なしで日常が回る) |
| 必須 | バックアップ状態(完了/残り/エラー)が iPhone 上で確認できる |
| 必須 | 保存済みメディアを取り出せる(最低限: ファイルとして) |
| 必要(Phase 2、決定済み) | **外出先からの** Web ブラウザによるタイムライン閲覧 |
| あとで | アルバム・お気に入りの同期、ゴミ箱 |
| やらない(当面) | 共有リンク、AI 検索、編集機能 |

## 2. 非機能要件の優先順位(トレードオフ方針)

衝突したら**上が勝つ**。この順序自体が本プロジェクトの最重要な意思決定。

1. **耐久性** — データを失わない
2. **完全性** — 壊れたデータを黙って保存しない・放置しない
3. **出口戦略** — このアプリが死んでも写真は取り出せる
4. **セキュリティ / プライバシー** — 写真を第三者に渡さない
5. **運用の手間** — 保守が月 1 時間を超えたら設計が間違っている
6. **クライアント負荷** — バッテリー・通信量・端末容量を食い潰さない
7. **コスト** — 増設はディスク買い切りのみ。保存量が増えるほど GB 単価が下がること(NFR-7)
8. **性能** — 快適さは欲しいが、上位を犠牲にしてまでは求めない
9. **可用性** — **最下位でよい**(理由は NFR-9)

> 典型的な Web サービスと逆で、可用性が最下位・耐久性が最上位。これが「単一ノードでよい」「その代わりバックアップと検証は手を抜かない」という設計方針の根拠になる。

## 3. 非機能要件(詳細)

### NFR-1 耐久性(最優先)

| 項目 | 目標 |
|---|---|
| バックアップ済みデータの喪失 | 事実上ゼロ。単一ディスク故障・サーバー全損でも失わない |
| コピー数 | **3-2-1 ルール**が理想: ① iPhone/iCloud(一次)② 自宅サーバー ③ オフサイト暗号化コピー。**③ は当面見送り(決定済み)** — 下記の受容リスク参照 |
| RPO(撮影→保存の遅延) | 自宅 Wi-Fi + 充電環境で **24 時間以内**。これを超える未バックアップ期間が iPhone 紛失時の喪失範囲になる |
| RTO(復旧時間) | 数日で可。急がない |
| メタデータ(DB) | originals と同格に保護。日次自動ダンプをバックアップ対象に含める |

**設計への影響**: バックアップ対象を `originals/ + DBダンプ` だけに絞れるよう、派生ファイル(サムネイル等)はすべて再生成可能なキャッシュとして扱う。

**受容リスク(決定済み・2026-07-16)**: オフサイトコピー導入までの間、「iPhone からは削除済みでサーバーにしか無い写真」はサーバーのディスク単一障害で失われ得る。緩和策として次のいずれかを運用ルールとする:

1. **オフサイト導入まで iPhone/iCloud 側の写真を削除しない**(既定。iPhone が 2 コピー目であり続ける)
2. サーバーに 2 台目ディスクを追加して日次ミラー([HARDWARE.md](HARDWARE.md) Stage 1)

### NFR-2 完全性

| 項目 | 目標 |
|---|---|
| 転送時の破損 | アップロード完了時にサーバーで SHA-256 再計算・検証。不一致は保存しない |
| 保存後の破損(ビット腐敗) | **月次スクラブ**(全 originals のハッシュ再検証)で検知し、オフサイトから復元 |
| 二重登録 | コンテンツハッシュ + DB の UNIQUE 制約で物理的に排除 |
| 沈黙障害の禁止 | 検証失敗・スクラブ失敗はクライアント通知まで届くこと。「気づいたら 3 年分壊れていた」を防ぐ |

### NFR-3 出口戦略(可搬性)

| 項目 | 目標 |
|---|---|
| 最悪ケースの取り出し | **サーバーもアプリも動かなくても**、ディスク上の `originals/` と DB ダンプだけから全写真を復元できること |
| 保存形式 | オリジナルのバイト列を無加工・非暗号化(自宅内)の**普通のファイル**として保存。独自コンテナ・独自暗号化でディスクに置かない |
| エクスポート | `YYYY/MM/` 階層 + 撮影日時ファイル名で書き出すツールを提供(Phase 3) |
| ロックイン回避 | DB は標準 SQL、ストレージはただのファイル or S3 互換。特定ベンダー専用機能に依存しない |

> 個人開発プロジェクトの現実的な死因は「作者(=自分)が飽きる・忙しくなる」。5 年後にメンテしていなくても写真だけは無事、を要件として明文化する。

### NFR-4 セキュリティ / プライバシー

**要件(決定済み)**: 外出先からの閲覧を可能にする。その際 **PII の漏洩防止を最優先**とする。本システムにおける PII とは: 写真そのもの(顔・自宅内観)、EXIF の GPS 位置情報(自宅・行動範囲が特定できる)、撮影日時のパターン、認証トークン。

| 項目 | 目標 |
|---|---|
| データの所在 | 写真・メタデータは運用者の管理下のみ。第三者クラウドへ置くのは**暗号化したオフサイトコピーのみ**(rclone crypt 等) |
| 認証 | **全メディア・メタデータ API は認証必須。未認証で 1 バイトも返さない。** URL は推測不能(UUID)にするが、URL 秘匿を認証の代替にしない |
| 外部アクセス方式 | **方式A(既定・推奨): Tailscale** — インターネットに公開せず、外出先の自分の端末から VPN 経由で閲覧。攻撃面ゼロで外出先閲覧の要件を満たせる。<br>**方式B(任意): リバースプロキシ公開** — 下記の硬化条件をすべて満たす場合のみ選択可 |
| 方式B の必須条件 | HTTPS(Let's Encrypt)/ 強度の高い認証(長いランダムトークンかパスキー)/ ログイン試行のレート制限 / 管理系エンドポイントの非公開 / 依存パッケージを更新し続ける運用 |
| GPS メタデータ | オリジナルには保持する(バックアップ目的のため加工しない)。閲覧・ダウンロードが認証内に閉じることで保護する。将来共有機能を作る場合は、共有用コピーから GPS EXIF を除去すること |
| 認証情報の保管 | デバイス毎トークン。1 台単位で失効可能(端末紛失時に備える)。DB にはハッシュのみ保存 |
| 通信 | 全経路 HTTPS/暗号化 |
| 想定脅威 | インターネットからの無差別スキャン、認証情報の漏洩、端末紛失。国家級・標的型は対象外 |
| E2E 暗号化 | **採用しない**(サーバー側サムネイル生成・出口戦略と両立しないため)。自宅サーバーの物理的管理で代替 |

### NFR-5 運用性

| 項目 | 目標 |
|---|---|
| 管理者 | 1 人(自分)。属人化してよいが、手順は README に残す |
| 保守工数 | **月 1 時間以内**。超えるなら設計を疑う |
| 導入 | `docker compose up -d` 一発。設定ファイル 1 つ |
| 更新 | イメージ pull + 再起動のみ。DB マイグレーション自動 |
| 監視 | ダッシュボードは作らない。「最終バックアップ成功日時」を iPhone アプリに表示し、**N 日間成功なしで通知**する、の 1 点のみ |
| 障害対応 | サーバーが数日死んでいても、復旧後にクライアントが自動で追いつくこと(人手の復旧作業ゼロ) |

### NFR-6 クライアント負荷(iPhone)

| 項目 | 目標 |
|---|---|
| モバイル通信 | **既定 0 バイト**(Wi-Fi のみ)。モバイル回線使用は明示的オプトイン |
| バッテリー | 自動バックアップは既定で**充電中のみ**実行 |
| 端末ストレージ | iCloud 最適化ライブラリの取り寄せはバッチ処理し、一時ファイルは即削除。端末の空き容量を一定以上残す |
| 体感 | バックアップ実行中もアプリ・端末の操作を妨げない |

### NFR-7 コスト

**方針(決定済み)**: 「**保存量が増えるほど GB 単価が下がる**」構成にする。基礎費用が固定の自宅サーバー + 買い切りディスクの増設を主保存とし、容量に比例して課金されるクラウドを主保存にしない。機材の比較・選定は [HARDWARE.md](HARDWARE.md)。

**上位目標(決定済み・2026-07-16)**: **累計コストが iCloud+ / Google One の同容量プランを下回ること。** 分析は [HARDWARE.md §7](HARDWARE.md)。この目標は次の 3 条件の下で成立する(条件が崩れる構成変更をしてはならない):

1. **3 年以上の利用**(損益分岐は約 2.5〜3 年後。既存 PC 流用なら 1 年台)
2. **データが増え続けること**(200 GB 以下ならクラウド月 ¥450 に、400 GB 以下なら Google AI Plus 月 ¥725 に勝ちにくい。iCloud 比なら 200 GB 超の時点で優位。前提 §0 の「200 GB〜で増加」が根拠)
3. **省電力機材(アイドル 10 W 級)+ オフサイトはコールドストレージ**(ホットなオブジェクトストレージを大容量で使うと前提が崩れる)

| 項目 | 目標 |
|---|---|
| 初期費用 | 5 万円以内(既存 PC 流用なら HDD 代のみ)。推奨構成は約 3.5 万円 |
| ランニング | 月 500 円以内(当面は電気代のみ。オフサイト追加時も +数百円に抑える) |
| クラウド比較 | iCloud 2 TB(月 ¥1,500)比: 3 年累計で同等、5 年以降は明確に下回ること。Google 最安経路(400 GB ¥725 → 2 TB)比でも 10 年累計で下回ること(分岐 4.4〜8 年、[HARDWARE.md §7](HARDWARE.md)) |
| スケール | 増設はディスクの買い切り(数円/GB)のみで済むこと。GB あたり総コストが成長とともに下がること |
| 開発コスト | 個人 + Claude Code で到達可能な規模に抑える(機能を足す前に運用性・耐久性を守る) |

### NFR-8 性能

| 項目 | 目標 |
|---|---|
| 初回フルバックアップ | 500 GB を**夜間充電 1〜2 週間**で完了(LAN 実効 20 MB/s 以上) |
| 日次差分 | 1 日分(〜100 点)を 10 分以内 |
| 閲覧(Phase 2 以降) | サムネイルグリッド表示: LAN 内 200 ms 以内、VPN 経由 1 秒以内 |
| スケール上限 | 50 万アセット・2 TB まで DB・UI が破綻しない(それ以上は対象外) |

### NFR-9 可用性(意図的に最下位)

| 項目 | 目標 |
|---|---|
| 稼働率 | 99% 程度(月数時間の停止は許容) |
| 根拠 | 一次データは iPhone 側に残っており、サーバー停止中の撮影分はクライアントがキューして復旧後に自動送信するため、**停止しても失うものがない** |
| 設計への影響 | HA・冗長化・ロードバランサは**作らない**。単一ノード + 再開可能アップロードで十分。浮いた複雑さを耐久性と運用性に回す |

## 4. 非機能要件 → 設計判断の対応表

| NFR | 導かれる設計(DESIGN.md 該当箇所) |
|---|---|
| NFR-1 耐久性 | 派生ファイルは再生成可能なキャッシュ扱い、バックアップ対象は originals + DB のみ(§4, §9) |
| NFR-2 完全性 | SHA-256 の E2E 検証付きアップロード、月次スクラブ(§2.2, §5, §9) |
| NFR-3 出口戦略 | オリジナル無加工・平文ファイル保存、エクスポートツール(§2.1, §4) |
| NFR-4 セキュリティ | 外出先閲覧は方式A(Tailscale・非公開)を既定、公開は硬化条件付きの方式Bのみ。デバイス毎トークン、E2E 暗号化は不採用(§2.5) |
| NFR-5 運用性 | Docker Compose 単一ノード、監視は「最終成功日時 + 通知」のみ(§1, §9) |
| NFR-6 クライアント負荷 | Wi-Fi + 充電中のみ既定、background URLSession、バッチ処理(§2.4, §7) |
| NFR-8 性能 | チャンクアップロード、サムネイル事前生成、カーソルページング(§5, §6) |
| NFR-9 可用性(低) | HA なし単一ノード、resumable upload + クライアント側キュー(§5) |

## 5. 決定事項と最終決定チェックリスト

### 5.1 決定済み(2026-07-16、発案者)

| # | 項目 | 決定内容 |
|---|---|---|
| 1 | ライブラリ規模 | **200 GB〜**。継続的に増加する前提で容量計画を立てる |
| 2 | 外出先からの閲覧 | **必要**。PII(位置情報・顔・生活パターン)が漏れないことを最優先条件とする(NFR-4) |

### 5.2 運用者が最終決定する項目

実装を始める前に、Claude Code と対話しながら以下を確定させ、チェックを埋めてコミットすること:

- [ ] **機材**: [HARDWARE.md](HARDWARE.md) の推奨(ミニ PC + USB HDD)を採用するか、既存機材を流用するか(§6 のチェックリストで適合確認)
- [ ] **外部アクセス方式**: 方式A(Tailscale・推奨)か、方式B(公開。NFR-4 の硬化条件が全て必須)か
- [ ] **自宅回線の確認**: 上り実効速度と CGNAT の有無(方式B の実現可否に影響。方式A なら回線を選ばない)
- [ ] **サーバー実装言語**: TypeScript か Go か(DESIGN.md はどちらでも成立。実装する Claude Code と相談して決めてよい)
- [ ] **iPhone 側の削除運用**: オフサイト導入まで「iPhone から写真を削除しない」を守れるか。守れないなら HARDWARE.md Stage 1(2 台目ミラー)を先に導入する
